# AGENTS.md for Production Code

`src/Chaos.BlazorAnalyzers` is the only production project. It contains Roslyn diagnostic analyzers (and, where a fix is unambiguous, the matching code fix providers) for Blazor code bases.

## Architecture Rules

- The project targets `netstandard2.0` and nothing else. The compiler host that loads the analyzer decides the runtime, so no `net10.0` target, no target-framework-conditional code, and no APIs beyond what `netstandard2.0` offers.
- The analyzer assembly must not carry third-party dependencies. Reference `Microsoft.CodeAnalysis.*` with `PrivateAssets="all"` and nothing else. Everything an analyzer references is loaded into the compiler's assembly load context, where a version conflict with the host or another analyzer breaks the build for the consumer.
- Analyzers must be pure: no file system access, no network access, no environment variables, no clock. Configuration comes from the `AnalyzerConfigOptions` of the analysis context, never from a file the analyzer reads itself.
- Analyzers must be thread-safe and free of mutable static state. Call `EnableConcurrentExecution()` in `Initialize`, and keep all per-analysis state in the callback's local scope or in a compilation-scoped start action.
- **Do not blanket-disable generated code analysis.** Razor compiles `.razor` files to C# marked `// <auto-generated/>`, so `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` — the usual default for analyzers — hides every component's markup, `@code` block, and `BuildRenderTree` from the analyzer. That is where most Blazor logic lives. Use `GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics` and exclude other generators' output explicitly if a rule needs to. `Analyze` alone is not enough: the analysis runs, but every diagnostic whose location falls inside the generated file is silently dropped. Diagnostics reported on Razor-generated syntax map back to the `.razor` file through its `#line` directives, so the user-facing location is correct.
- `DiagnosticSuppressor` has no `Initialize` and always sees generated code, including Razor output. A suppressor may therefore rely on generated constructs such as `RenderTreeBuilder.AddComponentReferenceCapture`.
- Register the narrowest action that answers the question — prefer `RegisterSymbolAction` and `RegisterOperationAction` over `RegisterSyntaxNodeAction`, and resolve well-known Blazor types once per compilation via `RegisterCompilationStartAction` instead of per node.
- Never compare types or attributes by name string in the analysis callback. Look the symbol up once with `Compilation.GetTypeByMetadataName` and compare with `SymbolEqualityComparer.Default`. An analyzer that finds no Blazor types in a compilation must report nothing rather than guess.
- Analyzers run on every keystroke in the IDE. Avoid allocations in hot paths, do not call `ToString()` on syntax nodes or symbols to make decisions, and never run an analysis that is superlinear in the size of the compilation.

## Diagnostic Rules

- Diagnostic IDs use the `KOS` prefix ("K-OS", for Chaos) followed by four digits, for example `KOS0001`. `BL` is taken by the ASP.NET Core component analyzers and must not be used.
- ID ranges are grouped by category: `KOS0001`–`KOS0999` component and parameter usage, `KOS1000`–`KOS1999` lifecycle and rendering, `KOS2000`–`KOS2999` state and disposal, `KOS8000`–`KOS8999` suppressions, `KOS9000`+ everything else. Assign the next free ID in the range; never reuse or renumber an ID that has shipped in a release.
- Suppressions get their own `KOS8xxx` block because a suppression ID and a diagnostic ID look identical in an `.editorconfig`, and a reader has to be able to tell which kind a rule is without looking it up.
- All `DiagnosticDescriptor` instances live in one central place, declared `static readonly`, so the full rule catalogue is visible in a single file.
- Every descriptor sets a category, a default severity, `isEnabledByDefault`, and a `helpLinkUri` pointing at the rule's documentation. A rule without documentation is not finished.
- Message and title strings are plain literals; do not add resource-based localization unless a plan asks for it explicitly.
- Default severity is `Warning` for a genuine bug and `Info` for a style or maintainability suggestion. Reserve `Error` for code that cannot work at runtime under any circumstances.

## Build & Packaging Rules

- The package is a development dependency: it ships the analyzer assembly under `analyzers/dotnet/cs` and contributes nothing to `lib`, so consumers do not get a runtime reference.
- `GenerateDocumentationFile` is on for this project (see `src/Directory.Build.props`), and `CODESTYLE.md` requires XML documentation for public APIs in reusable libraries. Document the public analyzer and descriptor surface.
- Do not add a code fix provider to the analyzer assembly. Code fixes depend on `Microsoft.CodeAnalysis.Workspaces`, which is not present in every compiler host; they belong in their own assembly, packaged alongside the analyzer.
- Adding, removing, or changing the severity of a shipped diagnostic is a breaking change for consumers who build with warnings as errors. It needs a plan and a release note.
