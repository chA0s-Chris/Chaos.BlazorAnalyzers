# KOS8003 — Member is assigned by a Blazor reference capture

| Item                  | Value                                    |
|-----------------------|------------------------------------------|
| Suppressed diagnostic | `CS8618`                                 |
| Suppressor            | `BlazorLifecycleNullabilitySuppressor`   |
| Enabled by default    | Yes                                      |

## Cause

A non-nullable member of a component deriving from `ComponentBase` is the target of an `@ref`
capture, and the compiler reports `CS8618` because nothing in the visible source assigns it.

```razor
<ChildComponent @ref="_child" />

@code {
    private ChildComponent _child;   // CS8618 without this suppression
}
```

## Why the warning is a false positive

The assignment exists, but only in code the Razor generator emits. For the markup above it produces
roughly:

```csharp
__builder.AddComponentReferenceCapture(1, (__value) => { _child = (ChildComponent)__value; });
```

The developer never writes that, so `CS8618` is reported against source that cannot be fixed without
`= null!`. The rule detects assignment to the member inside an `AddComponentReferenceCapture` or
`AddElementReferenceCapture` callback and suppresses the warning.

Because the generated `BuildRenderTree` and a `.razor.cs` code-behind are separate syntax trees, the
detection scans every partial declaration of the type. Both the `@code` layout and the code-behind
layout are supported.

## Captures through type inference

When the captured component is generic and its type argument is inferred, the generator does not
emit the capture inline. It routes the render call through a generated `TypeInference` helper and
passes the capture on as an `Action<T>` parameter, so the component's own `BuildRenderTree` never
mentions `AddComponentReferenceCapture`:

```csharp
// in the component
TypeInference.CreateChild_0(__builder, 0, 1, (__value) => { _child = (Child<TValue>)__value; });

// in the generated helper
public static void CreateChild_0<TValue>(RenderTreeBuilder __builder, int seq, int __seq0, Action<Child<TValue>> __arg0)
    => __builder.AddComponentReferenceCapture(__seq0, (__value) => { __arg0((Child<TValue>)__value); });
```

The rule follows that one level of indirection. A lambda that assigns the member and is passed to a
method counts as a capture when that method hands the *corresponding* parameter to a reference
capture of its own. One level is all the generator emits, so the rule does not recurse further.

Specifying the type argument explicitly — `<Child TValue="int" @ref="_child" />` — takes the inline
path instead and was always covered.

## Important caveat

A captured reference is **null until after the component first renders**. This suppression tells the
compiler the member is assigned; it does not make the member safe to use early:

```csharp
protected override void OnInitialized()
    => _child.DoSomething();        // NullReferenceException at run time
```

Use captured references from `OnAfterRender`/`OnAfterRenderAsync` or from event handlers. The risk
is the same one `= null!` carries today; this rule neither adds nor removes it.

## Limitations

- **The capture method is matched syntactically** by name and callback shape, scoped to types
  deriving from `ComponentBase`. A user-defined method named `AddComponentReferenceCapture` on a
  component would also match.
- **Forwarding is followed one level deep.** The forwarded call itself is resolved by symbol, so an
  unrelated method with a matching name does not qualify, but a chain of two helpers would not be
  followed. The Razor generator emits exactly one level.
- **`AddElementReferenceCapture` is recognised but currently unreachable** for `CS8618`, because
  `ElementReference` is a struct and never produces the warning. It is handled so the rule expresses
  "reference capture" rather than "component capture".

## How to turn it off

```ini
dotnet_diagnostic.KOS8003.severity = none
```
