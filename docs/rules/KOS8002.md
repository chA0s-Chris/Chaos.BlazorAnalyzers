# KOS8002 — Member is assigned by Blazor dependency injection

| Item                  | Value                                    |
|-----------------------|------------------------------------------|
| Suppressed diagnostic | `CS8618`                                 |
| Suppressor            | `BlazorLifecycleNullabilitySuppressor`   |
| Enabled by default    | Yes                                      |

## Cause

A non-nullable property of a component deriving from `ComponentBase` is marked `[Inject]`, and the
compiler reports `CS8618` because the property is not assigned by the time the constructor exits.

## Why the warning is a false positive

Blazor performs property injection after constructing a component and before any lifecycle method
runs. The resolution goes through `GetRequiredService`, which **throws** when the service is not
registered rather than assigning null. The property is therefore non-null on every path the
developer can observe, or the component never comes into existence at all.

```csharp
public partial class Dashboard : ComponentBase
{
    [Inject] public IDownloadTokenProvider TokenProvider { get; set; }   // CS8618 without this suppression
}
```

This is the strongest of the three suppressions: it rests on a framework guarantee rather than on a
syntactic heuristic, which is why it applies without inspecting any method bodies.

## Scope

- **Properties only.** `InjectAttribute` targets properties and indexers, so `[Inject]` on a field
  is a compiler error (`CS0592`) and never reaches this rule.
- **Components only.** The declaring type must derive from `ComponentBase`. `[Inject]` on a plain
  class is never populated by Blazor, so `CS8618` there is a real warning and is left alone.

`[Parameter]` and `[CascadingParameter]` members are deliberately **not** suppressed. The framework
does not guarantee that a parameter is supplied or that a cascading value has a provider, so those
warnings are genuine.

## How to turn it off

```ini
dotnet_diagnostic.KOS8002.severity = none
```

`CS8618` is then reported again. The common alternatives are `= default!` on each injected property
or making them nullable, both of which this rule exists to make unnecessary.
