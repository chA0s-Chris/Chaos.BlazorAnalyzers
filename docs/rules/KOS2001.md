# KOS2001 — Blazor component does not dispose a JS interop reference

| Item     | Value                     |
|----------|---------------------------|
| Category | Reliability               |
| Severity | Warning                   |
| Analyzer | `JsInteropDisposalAnalyzer` |

## Cause

A component deriving from `ComponentBase` assigns an `IJSObjectReference` (for example the result of
a JavaScript module import) or a `DotNetObjectReference<T>` to a field or property, and never
disposes it.

## Rule description

Both references hold resources the garbage collector cannot reclaim on its own. An
`IJSObjectReference` keeps an entry alive in the JavaScript-side object registry, and a
`DotNetObjectReference<T>` roots the .NET object it wraps. A component that creates one owns it and
must release it.

`ComponentBase` does not implement `IDisposable`. The renderer checks at runtime whether a component
implements `IDisposable` or `IAsyncDisposable` and calls it, so disposal is opt-in and easy to
forget. The leak is most damaging in Blazor Server, where a circuit can live for hours.

## How to fix violations

Implement `IAsyncDisposable` and dispose the reference:

```csharp
@implements IAsyncDisposable

@code {
    private IJSObjectReference? _module;

    protected override async Task OnAfterRenderAsync(Boolean firstRender)
    {
        if (firstRender)
        {
            _module = await JS.InvokeAsync<IJSObjectReference>("import", "./MyComponent.razor.js");
        }
    }

    public async ValueTask DisposeAsync()
    {
        if (_module is not null)
        {
            await _module.DisposeAsync();
        }
    }
}
```

## When to suppress

Suppress when the reference is deliberately handed to another owner that disposes it. Do not
suppress merely because the component is short-lived; in Blazor Server the circuit, not the
component, determines how long the leak persists.

## Related rules

`CA1001` and `CA2213` cover disposable fields whose ownership the compiler can infer from a
constructor or field initializer. They do not fire here, because these references are produced by a
method call (`InvokeAsync`, `DotNetObjectReference.Create`) rather than by `new`.
